# Isolated camera decoder — source checkpoint

Final frozen Windows EXE verification: MC510 TCP and UDP, 12 seconds each, both delivered and painted 145 frames at 2304×1296 in the offscreen Qt preview, one capture connection per run, exit code 0, clean shutdown and no last error. This validates the frozen spawn path and actual frame rendering, not a new installer release or a codec/performance certification.

The default `CameraWorker` now launches one native decoder process per camera using Python's spawn context. OpenCV/FFmpeg opens, reads and releases inside that process. A timed-out or crashed decoder is retired, and the existing bounded retry policy can reconnect without retaining stale frames. Preview and inference still share one camera worker and one RTSP session.

Each decoder has one shared BGR buffer, capped at 3840×2160×3 bytes (about 23.7 MiB), plus the existing detached latest frame and one-frame preview queue. The parent requests one frame at a time; no video queue grows in the child. Current transfer copies each delivered image. Multi-camera RAM and throughput need measurement before making capacity claims.

Opening has a 10-second parent deadline including spawn/import time. Reading has a 4-second parent deadline. OpenCV additionally receives 3-second native open/read timeouts. The parent checks cancellation every 50 ms while waiting. Release waits 0.2 seconds, then terminates a non-responsive decoder and waits at most one second, with a final kill/join fallback. A frozen desktop entry calls `multiprocessing.freeze_support()` before importing GUI/CLI modules, as required by [PyInstaller's multiprocessing documentation](https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html#multi-processing).

`CameraConfig.transport` accepts `tcp` (default) or `udp`; `camera-test --transport` exposes both for diagnostics. The child sets the [OpenCV FFmpeg capture options](https://docs.opencv.org/4.x/d6/dea/tutorial_env_reference.html) in its own environment. Cameras cannot overwrite each other's transport settings. Credentials are passed through the private multiprocessing bootstrap channel, never command-line arguments or diagnostic results. The source string remains in application memory as needed for reconnects.

Tests use actual spawned children to exercise open hangs, read hangs, process crashes, stuck native release, cancellation, independent TCP/UDP environments and detached frames. The full suite passed 113 tests before the diagnostic transport argument was added; the final affected 21 tests passed after that addition and the intentional-stop error handling correction.

Real MC510 at the user-designated address, source-mode tests, 12 seconds each: TCP 159 decoded frames, first frame 2.60 seconds; UDP 161 frames, first frame 2.35 seconds. Both produced 2304×1296 frames and stopped. These first measurements recorded `stream_interrupted` on intentional stop; that misleading status was corrected afterward. The frozen diagnostic results accompany the checkpoint separately.

Remaining work: persist transport choice and expose it in camera setup, explicit bounded TCP/UDP fallback, richer RTSP error classification, codec/hardware decode diagnostics, ONVIF, long-running/multi-camera load tests and parent-crash orphan cleanup. This design bounds a decoder hang while the supervising application remains alive; it is not yet a Windows Job Object guarantee against orphan processes if the parent itself crashes. Source and frozen development verification do not constitute a new signed installer release.
